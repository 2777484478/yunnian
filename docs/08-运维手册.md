# 08 · 运维手册

> 这份文档只回答一件事：**这套服务部署在服务器上之后，日常怎么维护**。
> 装新环境请看 [`../README.md` 的「安装与部署」](../README.md#安装与部署)，这里不重复。

---

## 0. 先记住三件事

**① 代码走 git，不走「手动拷文件」。**

```bash
cd /opt/yunnian && git pull        # 拉最新代码
docker compose build app           # 重新出镜像
docker compose up -d app           # 替换容器
```

**② 前后端都编进镜像，没有热更新。**

`Dockerfile` 是三阶段的：`node:22` 编前端 → `golang:1.26` 编后端 → `alpine` 打最终镜像。
任何一行代码改动，都必须 `docker compose build app` 重新出镜像。**`restart` 不行**——
它只是把旧镜像里的进程重启一遍，新代码根本没进去。

**③ 只有三个容器。**

`yunnian-app` / `yunnian-mysql` / `yunnian-redis`，全部 `restart: unless-stopped`（机器重启会自动拉起）。

## 2. 更新代码

### 2.1 一次性：把部署目录纳入 git 管理

如果 `/opt/yunnian` 之前是用 `rsync` 覆盖上去的，`git pull` 会因为「本地有大量修改」而失败
（`git status` 会看到一堆 `M`）。先对齐一次：

```bash
cd /opt/yunnian

# ① 先确认这两份**不在 git 里**的文件还在（它们是 .gitignore 的，reset 不会动）
ls -l .env backend/configs/config.yaml

# ② 丢弃 rsync 覆盖产生的本地修改，对齐到远端
git fetch origin
git reset --hard origin/main
```

> ⚠️ `git reset --hard` 会丢弃工作区的所有改动。执行前确认上面那两个文件存在——
> `.env`（含 `YUNNIAN_MASTER_KEY`）丢了，库里所有加密凭据都解不开。

之后就是普通的 git 流程了。

### 2.2 日常更新（三步）

```bash
cd /opt/yunnian

# ① 拉代码
git pull

# ② 重新出镜像（3~6 分钟，改得多会更久）
docker compose build app

# ③ 替换容器（中断约 10 秒）
docker compose up -d app

# 确认活着
curl -s --noproxy '*' -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/healthz
```

`healthz` 返回 `200` 就是好了。

### 2.3 看一眼改了什么

```bash
git log --oneline -5          # 最近 5 次提交
git diff HEAD@{1} --stat      # 这次 pull 动了哪些文件
```

**只改了前端**：命令一样。BuildKit 会跳过 `go build` 那一段（`backend/` 没变），所以会快一些。

### 2.4 如果 git 拉不动

（网络抽风时）可以从开发机 rsync 覆盖过去，再 `build` + `up`：

```bash
rsync -a --exclude node_modules --exclude dist \
  -e 'ssh -i ~/.ssh/id_ed25519_github' \
  backend/ frontend/ root@<服务器>:/opt/yunnian/
```

**注意**：这条路会让工作区变脏，下次 `git pull` 前要 `git reset --hard origin/main`（同上，`.env` 和 `config.yaml` 不受影响）。

## 3. 重启与停止（不涉及代码改动）

| 目的 | 命令 |
|---|---|
| 重启应用（配置变了，代码没变） | `docker compose restart app` |
| 重建并替换（镜像更新了 / compose 改了） | `docker compose up -d app` |
| 停止应用 | `docker compose stop app` |
| 启动应用 | `docker compose start app` |
| 停止全部（保留数据） | `docker compose stop` |
| **⚠️ 别用** | `docker compose down` —— 加 `-v` 连数据卷一起删 |
| 看日志 | `docker compose logs -f --tail=200 app` |
| 看状态 | `docker compose ps` |

### 3.1 配置文件是挂载的，改完不用重建

```yaml
# docker-compose.yml
- ./backend/configs/config.yaml:/app/configs/config.yaml:ro
```

改 `/opt/yunnian/backend/configs/config.yaml`（SMTP、超时、阈值这些）之后：

```bash
docker compose restart app     # 就够，不需要 build
```

## 4. 改了什么要做什么

| 改动 | 需要做的 |
|---|---|
| 前端页面 / 样式 | `git pull` → `build app` → `up -d app` |
| 后端 Go 代码 | 同上 |
| `configs/config.yaml` | 直接改 → `restart app` |
| `docker-compose.yml` | `git pull` → `up -d`（会重建容器，不用 build） |
| 数据库表结构（`model/` 里的 struct） | 代码里的 AutoMigrate 自动建表 / 加列，**不用手工 SQL** |
| 手工改数据 | 先备份（见 §7） |

## 5. 看运行状态

```bash
cd /opt/yunnian

docker compose ps                                      # 三个容器的状态与健康
curl -s --noproxy '*' http://127.0.0.1:8080/healthz    # 后端活着吗
docker compose logs --tail=100 app                     # 最近日志
docker compose logs -f app                             # 跟踪（Ctrl+C 退出）
docker stats --no-stream                               # CPU / 内存实时占用
```

**只看错误**：

```bash
docker compose logs --since 30m app 2>&1 | grep -E 'level=ERROR|level=WARN' | tail -30
```

## 6. 磁盘维护（每月看一次）

### 6.1 为什么长得这么快

`Dockerfile` 每次构建都会产生一层缓存：

```
npm ci          → node_modules（约 500MB）
npm run build   → 前端产物层
go mod download → Go 依赖（约 200MB）
go build        → 编译层
COPY            → 源码层
```

BuildKit 会**保留所有层**用于加速下次构建。构建几十次之后，缓存能堆到 **20~30GB**
（2026-11-27 清过一次，回收 **31.76GB**，磁盘 93% → 62%）。

### 6.2 先看分布

```bash
df -h /                # 整体
docker system df       # Docker 各部分占用与「可回收」
```

### 6.3 清理（按安全性排序）

| 命令 | 典型回收 | 风险 |
|---|---|---|
| `docker builder prune -af` | **20~32GB** | **无**。只是下次构建慢几分钟 |
| `docker image prune -f` | 几 GB | 无。只删 dangling（无 tag 的中间层） |
| `docker image prune -a` | 7~8GB | 中。会删未被容器使用的基础镜像，下次构建要重新 pull |
| `docker volume prune -f` | 4GB | **高**。会删未挂载的卷，务必先看名字 |
| `docker system prune -a --volumes` | 最大 | **危险**，别用 |

**推荐**：每次只跑第一条，够了就停。

```bash
docker builder prune -af && df -h /
```

### 6.4 卷要看清楚再删

```bash
docker volume ls -f dangling=true | head -30
```

**绝不能删的**：`yunnian-mysql-data`（数据库）、`yunnian-data`（应用数据）。
看到名字里带 `mysql` / `data` 的，先停下来确认。

## 7. 备份

完整备份放在开发机的 `~/yunnian-backups/<日期>/`（不在仓库里，也不在服务器上）。

一份完整备份必须包含四样：

| 文件 | 说明 |
|---|---|
| `yunnian-db.sql.gz` | 数据库全量 |
| `env.bak` | **`YUNNIAN_MASTER_KEY`** —— 丢了它，库里 13 条加密凭据（kubeconfig / GitLab token / 模型 key）全部解不开 |
| `backend-config.yaml` | 真实配置文件（SMTP 等），被 `.gitignore` 忽略 |
| `docker-config.json` | Harbor 登录态（自建构建推镜像用） |

详细步骤见备份目录里的 `RESTORE.md`。

**建议时机**：改数据库结构、加新表、批量改数据之前，各备一次。

## 8. 故障速查

| 现象 | 先查什么 |
|---|---|
| 页面打不开 / 502 | `docker compose ps`；`curl http://127.0.0.1:8080/healthz`；`docker compose logs --tail=50 app` |
| 某个环境数据出不来，其他正常 | 该集群连通性：`curl -k -m 5 -o /dev/null -w "%{http_code} %{time_total}\n" https://<集群IP>:6443/healthz` |
| 某个环境要等十几秒 | 同上，看 `time_total` 与 `time_connect` 是否陡增；对比 `time_appconnect - time_connect`（差值大是 TLS 阶段） |
| 邮件通知失败 | `docker exec yunnian-app sed -n '/^  email:/,/^  [a-z]/p' /app/configs/config.yaml` 看容器里是不是真配置 |
| 构建卡住 | `docker ps` 看构建容器；`docker compose logs --tail=100 app 2>&1 \| grep -i build` |
| 磁盘满 / MySQL 起不来 | `df -h /`，按 §6 清 |
| 部署队列已满 | 默认并发 1、队列 50。见「系统管理 › 第三方集成 › 平台参数」 |

## 9. 机器重启后

容器都是 `restart: unless-stopped`，Docker 起来会自动拉起。确认一下：

```bash
docker compose ps
curl -s --noproxy '*' -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/healthz
```

如果 `app` 起来了但页面报数据库错，等 MySQL 变 `healthy` 后 `docker compose restart app` 一次。

## 10. 本地开发环境

```bash
~/yunnian-local.sh start     # 起 mysql/redis + 后端，等 healthz 通才返回
~/yunnian-local.sh stop      # 停（用 stop 不用 down，保数据卷）
~/yunnian-local.sh status
~/yunnian-local.sh logs
```

访问 `http://127.0.0.1:8080`，账号 `admin / yunnian@2026`。

> ⚠️ **本地库里的 kubeconfig 是真实有效的**。本地页面点「发布 / 回滚 / 扩缩容」会真的改线上集群。
> 只测 UI 和查询是安全的；要测部署，先在本地库把 `secret_credential` 里的 kubeconfig 换成假的。
