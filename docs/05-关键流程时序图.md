# YunNian 云辇 · 关键流程时序图

> 三个核心流程：**CI 构建**、**CD 部署（含审批）**、**版本回滚**；
> 另附 **AI 失败归因** 与 **Webhook 自动构建** 两个辅助流程。

---

## 1. 一键编译（CI 构建 + 实时日志）

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户（开发）
    participant FE as 前端
    participant API as YunNian Server
    participant DB as MySQL
    participant RD as Redis
    participant Q as 任务队列
    participant R as CI Runner
    participant GL as GitLab
    participant HR as Harbor
    participant NTF as 通知模块

    U->>FE: 点击「编译」→ 选分支 + 覆盖构建参数
    FE->>FE: 生成 idempotencyKey = {key}:{branch}:{commitId}
    FE->>API: POST /api/v1/builds
    API->>API: 鉴权（build:trigger）+ 参数校验 + 限流检查
    API->>RD: GET yn:webhook:dedup / idempotency 查重

    alt 10 分钟内已提交过相同 commit
        API-->>FE: 40902 + 已有任务信息
        FE-->>U: 提示「已存在构建任务」并跳转
    else 新任务
        API->>DB: INSERT build_record (status=queued, params_snapshot)
        API->>DB: UPDATE project SET build_seq = build_seq + 1
        API->>RD: XADD yn:build:{id}:log（写入"任务已入队"首行）
        API->>Q: push {buildId, projectKey, branch, params}
        API->>DB: INSERT audit_log（触发构建）
        API-->>FE: 201 {id, buildNo, queuePosition, logStreamUrl}
        FE->>FE: 跳转构建记录页，toast「构建任务已提交」
        FE->>API: GET /builds/{id}/logs/stream（EventSource）

        R->>Q: 领取任务（BLPOP）
        R->>DB: UPDATE build_record SET status=running, runner_id, started_at
        R->>RD: XADD 日志流（clone 阶段）
        RD-->>API: XREAD BLOCK 增量日志
        API-->>FE: SSE event: log / id: seq / data:{seq,ts,level,line}
        API-->>FE: SSE event: status {status:running, progress:15, stage:拉取代码}

        R->>GL: git clone --depth 1 -b {branch}
        GL-->>R: 源码
        R->>RD: XADD（依赖安装 / 编译阶段日志）

        alt buildMethod = dockerfile
            R->>R: docker build --platform {platform} --provenance=false -f {dockerfile} -t {image} {context}
            Note over R: --provenance=false 必须有：BuildKit 默认挂 attestation 会把产物<br/>变成 manifest list，推到 Harbor 报 manifest invalid
        else buildMethod = jenkins
            R->>GL: 触发 Jenkins Job（POST buildWithParameters）
            R->>R: 轮询 Jenkins 构建结果
        else buildMethod = script
            R->>R: 把 buildScript 落盘为 build-{id}.sh，注入 YUNNIAN_* 变量后 `sh 文件`
            Note over R: 不 sh -c：脚本里报错的行号要指向脚本自己那一行
            R->>GL: 脚本内 git clone（凭据由 GIT_ASKPASS 预置，脚本里不出现）
            R->>DR: 脚本内 docker run {BUILD_IMAGE} 编译 → docker build -t $YUNNIAN_IMAGE
            R->>HR: 脚本内 docker push $YUNNIAN_IMAGE
            R->>R: 核验 $YUNNIAN_IMAGE 在构建机上确实存在
            alt 镜像不存在
                R-->>R: SCRIPT_NO_IMAGE（退出码 0 也判失败）
                Note over R: 一段只做 clone 的脚本退出码是 0，构建记录会写"成功"、<br/>日志一片祥和，而镜像列表什么都没有
            end
        end

        R->>R: 按 tagPattern 渲染 Tag（默认 v{buildNo}，支持 {branch}/{commitId}/{timestamp}/{date}）
        R->>R: docker push {registry}/{imageName}:{tag}
        R->>HR: 推送镜像层
        HR-->>R: digest = sha256:9f21c4d8...

        alt 推送成功
            R->>DB: INSERT image_record（digest/size/branch/commit/pushed_at）
            R->>DB: UPDATE build_record SET status=success, duration, image_record_id
            R->>RD: XADD 末行 + SET yn:build:{id}:done = {status:success,...}
            RD-->>API: 读到 done
            API-->>FE: event: status {status:success, progress:100, image, digest}
            API-->>FE: event: end {reason:finished}
            FE->>FE: 关闭 EventSource，展示镜像地址 + Digest + 复制/下载按钮
            Note over API,NTF: 构建「成功不推送」。平台只在 build_failed / build_interrupted /<br/>deploy_failed / deploy_interrupted / deploy_pending_approval 五个事件上投递<br/>（见 docs/03 §10）；原先这里写的 build_success 与「邮件/钉钉/企微/飞书/Webhook」都已不存在
        else 构建失败（非 0 退出 / 超时）
            R->>DB: UPDATE build_record SET status=failed, error_code, log_url
            R->>RD: XADD 错误行 + SET done = {status:failed}
            API->>API: 异步调用 AI 归因（日志 → 分类 → 建议）
            API->>DB: UPDATE build_record SET ai_diagnosis = {...}
            RD-->>API: 读到 done
            API-->>FE: event: status {status:failed} + AI 归因卡
            API-->>FE: event: end {reason:finished}
            API->>NTF: 投递 build_failed（含 AI 建议摘要）
        end
    end

    Note over U,FE: 任意时刻用户都可点「取消」
    U->>FE: 点击「取消构建」
    FE->>API: POST /builds/{id}/cancel
    API->>RD: SET yn:build:{id}:cancel = 1
    API->>DB: INSERT audit_log（取消构建）
    R->>RD: 轮询到 cancel 标记
    R->>R: SIGTERM 子进程 + docker kill
    R->>DB: UPDATE build_record SET status=canceled
    RD-->>API: 读到 done
    API-->>FE: event: end {reason:canceled}
```

## 2. 部署流程（含正式区审批）

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户（运维/开发）
    participant FE as 前端
    participant API as YunNian Server
    participant DB as MySQL
    participant RD as Redis
    participant K8S as Kubernetes
    participant NTF as 通知模块

    U->>FE: 环境详情 → 服务 → 「部署」
    FE->>API: GET /projects/{key}/images?limit=5（拉可选镜像版本）
    API-->>FE: 镜像版本列表（默认最新）
    U->>FE: 选项目/镜像/副本数 → 填写参数 → 确认部署
    FE->>API: POST /api/v1/deployments

    API->>API: 鉴权（deploy:{envKey}） + 环境启用校验
    API->>RD: SET yn:lock:deploy:{env}:{svc} NX PX 1800000
    alt 未拿到锁（该服务已有部署进行中）
        API-->>FE: 40901 + 冲突部署单号
        FE-->>U: 提示「有部署进行中，请等待或取消」
    end

    API->>DB: 校验 image_record 存在且未清理
    API->>DB: INSERT deploy_record
    API->>DB: INSERT deploy_step × 4（全部 pending）
    API->>DB: INSERT audit_log（执行部署 + diff）

    alt 环境 need_approval = true（如正式区）
        API->>DB: deploy_record.status = pending_approval
        API->>NTF: 通知审批人（运维示例/林曦）
        API-->>FE: 201 {status: pending_approval, approvers}
        FE-->>U: 提示「已提交审批」
        actor A as 审批人
        A->>FE: 部署记录 → 「审批」
        FE->>API: POST /deployments/{id}/approve
        API->>API: 鉴权（deploy:approve）
        API->>DB: UPDATE deploy_record SET status=queued, approver_id, approved_at
        API->>DB: INSERT audit_log（审批通过）
    else 免审批环境
        API->>DB: deploy_record.status = queued
    end

    API->>RD: push yn:deploy:queue {deployId}
    API-->>FE: logStreamUrl
    FE->>API: GET /deployments/{id}/logs/stream（SSE）

    Note over API,K8S: 步骤 1/4 拉取镜像
    API->>DB: UPDATE step[1]=running
    API->>K8S: kubectl set image deployment/{svc} app={image}<br/>（或 patch Deployment spec）
    K8S->>K8S: 调度节点 + 拉取镜像
    API-->>FE: event: status {status:progressing, progress:25, stage:拉取镜像}

    Note over API,K8S: 步骤 2/4 创建 Pod
    API->>K8S: watch Pod 事件
    K8S-->>API: Pod Pending → ContainerCreating → Running
    API->>DB: UPDATE step[2]=success
    API-->>FE: event: log（Pod 调度日志）+ status progress:50

    Note over API,K8S: 步骤 3/4 健康检查
    API->>K8S: 轮询 readiness probe 状态
    K8S-->>API: Readiness probe 200（第 1 个副本就绪）

    Note over API,K8S: 步骤 4/4 就绪确认
    API->>K8S: kubectl rollout status --timeout=600s
    K8S-->>API: deployment "svc" successfully rolled out

    alt 全部副本就绪
        API->>DB: UPDATE service_instance<br/>SET current_image_id, current_tag, ready_replicas, status=running, applied_revision
        API->>DB: UPDATE deploy_record SET status=success, duration, finished_at
        API->>DB: UPDATE image_record SET deployed_envs（同步冗余字段）
        API->>DB: UPDATE deploy_step 全部 success
        API->>DB: INSERT audit_log（部署成功）
        API->>RD: DEL yn:lock:deploy:{env}:{svc}
        API-->>FE: event: status {status:success, progress:100} + event: end
        Note over API,NTF: 部署「成功不推送」（原先这里写的 deploy_success 已不存在）
        FE-->>U: 服务状态刷新为「运行中」
    else 超时 / 探针失败 / Pod CrashLoopBackOff
        API->>DB: UPDATE deploy_record SET status=failed, error_code=PROBE_FAILED
        API->>K8S: 拉取 Pod 事件与容器日志尾部
        API->>API: AI 诊断（日志 + 事件 → 原因 + 建议回滚目标）
        API->>DB: UPDATE deploy_record SET ai_diagnosis
        API->>RD: DEL yn:lock:deploy:{env}:{svc}
        API-->>FE: event: status {status:failed} + AI 诊断卡
        API->>NTF: 投递 deploy_failed（含建议）
        FE-->>U: 展示 AI 诊断 + 「按建议回滚」按钮
    end
```

### 2.1 回滚与部署的关系

> 回滚在实现上是**部署的特殊形态**：以历史 `image_record` 为目标镜像创建新的 `deploy_record`，
> 并在 `rollback_record` 中记录 `from_image` / `to_image` / `reason`。
> 这样部署状态机、日志通道、审计埋点全部复用，无需第二套逻辑。

## 3. 版本回滚流程

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户（运维）
    participant FE as 前端
    participant API as YunNian Server
    participant DB as MySQL
    participant RD as Redis
    participant K8S as Kubernetes
    participant NTF as 通知模块

    Note over U,K8S: 入口 A：人工发现异常主动回滚
    U->>FE: 环境详情 → 服务 → 「回滚」
    FE->>API: GET /services/{id}/versions
    API->>DB: 查 service_instance + image_record + deploy_record 历史
    API-->>FE: 历史版本列表（镜像/Tag/部署时间/部署人/状态/是否当前/是否上一稳定版本）
    FE-->>U: 弹窗展示版本列表，默认选中「上一个稳定版本」

    Note over U,K8S: 入口 B：AI 诊断建议回滚
    API->>API: 部署失败 → AI 诊断 → recommendedAction.type = rollback
    API-->>FE: 诊断卡带「按建议回滚」按钮
    U->>FE: 点击「按建议回滚」（自动带入 targetImageId）

    U->>FE: 填写回滚原因（必填）→ 「确认回滚」
    FE->>API: POST /api/v1/rollbacks

    API->>API: 鉴权（rollback:execute，按环境校验）
    API->>RD: SET yn:lock:deploy:{env}:{svc} NX PX 1800000
    alt 未拿到锁
        API-->>FE: 40901 有部署/回滚进行中
    end

    API->>DB: 校验 targetImage 存在于 image_record 且 Harbor 中仍可拉取
    alt 镜像已被清理
        API-->>FE: 40400 + 提示「该版本镜像已被清理，请选择其他版本」
    end

    API->>DB: INSERT rollback_record(from_image, to_image, reason, trigger_type, operator)
    API->>DB: INSERT deploy_record(parent_deploy_id = 当前部署, image = to_image)
    API->>DB: INSERT deploy_step × 4
    API->>DB: INSERT audit_log（执行回滚，含 from/to diff）
    API->>NTF: 通知回滚执行（运维值班群）
    API-->>FE: 201 {rollbackId, deployNo, logStreamUrl}
    FE->>API: GET /rollbacks/{id}/logs/stream（SSE）

    API->>K8S: kubectl rollout undo / set image → {to_image}
    K8S->>K8S: 滚动创建新 ReplicaSet，逐步替换旧 Pod

    loop 直到全部就绪或超时（默认 600s）
        K8S-->>API: Pod 状态更新
        API->>DB: UPDATE deploy_step 进度
        API-->>FE: event: log / status（实时进度）
    end

    alt 回滚成功
        API->>DB: UPDATE rollback_record SET status=success, duration_sec
        API->>DB: UPDATE deploy_record SET status=rolled_back
        API->>DB: UPDATE service_instance SET current_image_id=to_image, status=running
        API->>DB: UPDATE image_record.deployed_envs（旧的移除、新的加入）
        API->>DB: INSERT audit_log（回滚成功）
        API->>RD: DEL yn:lock:deploy:{env}:{svc}
        API-->>FE: event: status {status:success} + end
        Note over API,NTF: 回滚「成功不推送」：平台没有 rollback_executed 这个触发点
        FE-->>U: 展示「回滚成功」+ 版本变化对比（异常版本 → 目标版本）
    else 回滚失败
        API->>DB: UPDATE rollback_record SET status=failed
        API->>DB: UPDATE deploy_record SET status=failed
        API->>API: 二次 AI 诊断（可能是镜像/配置/集群问题）
        API->>RD: DEL yn:lock:deploy:{env}:{svc}
        API-->>FE: event: status {status:failed}
        API->>NTF: 投递 deploy_failed（回滚本身就是一次发版，走 failDeploy 同一条失败路径）
        FE-->>U: 提示人工介入 + 展示诊断
    end
```

## 4. AI 失败归因流程

```mermaid
sequenceDiagram
    autonumber
    participant API as YunNian Server
    participant RD as Redis
    participant AI as AI 模块
    participant LLM as 大模型（内部/外部）
    participant DB as MySQL
    participant LIB as 历史失败样本库

    Note over API,DB: 触发时机：构建失败 / 部署失败（异步，不阻塞主流程）
    RD-->>API: 读到 done = {status:failed, buildId}

    API->>RD: 取日志尾部 N 行（默认 200 行）+ 错误行上下文 ±20 行
    API->>DB: 取项目配置（buildMethod / registry / 参数快照）
    API->>DB: 取该服务近 30 天同类失败记录

    API->>AI: analyze({logs, projectConfig, cluster?})
    AI->>AI: 预处理：脱敏（token/密码/IP）+ 错误行提取 + 阶段定位
    AI->>LIB: 检索相似失败样本（向量相似度 TOP 5）
    AI->>LLM: 结构化提示（日志 + 配置 + 相似样本）→ 要求返回 JSON

    LLM-->>AI: {reason, suggestion, confidence, errorCode, evidence[]}

    alt confidence ≥ 0.7
        AI->>AI: 生成 errorCode 分类（DEP_RESOLVE / PUSH_DENIED / OOM / TS_COMPILE / PROBE_FAILED ...）
        AI->>DB: UPDATE build_record/deploy_record SET error_code, ai_diagnosis
        AI->>DB: 写入样本库（脱敏后的日志特征 → errorCode），持续提升检索命中率
        API-->>API: 前端轮询/SSE 拿到诊断 → 展示归因卡
    else confidence < 0.7
        AI->>DB: 仅存 ai_diagnosis 但不展示强建议
        API-->>API: 前端展示「暂无高置信度结论，请人工排查」+ 日志直达
    end

    Note over API,LLM: 若 LLM 调用超时/失败 → 降级为规则引擎（正则匹配常见错误码），<br/>保证「至少给出分类」而不阻塞用户。
```

## 5. Webhook 自动构建流程

```mermaid
sequenceDiagram
    autonumber
    participant GL as GitLab
    participant API as YunNian Server
    participant RD as Redis
    participant DB as MySQL
    participant Q as 任务队列
    participant NTF as 通知模块

    GL->>API: POST /webhooks/gitlab（Push Hook）
    API->>API: 校验 X-Gitlab-Token 签名
    alt 签名无效
        API-->>GL: 401，并记录审计（疑似伪造）
    end

    API->>DB: 按 git_url 反查 project（未匹配 → 200 忽略）
    API->>API: 分支白名单匹配 auto_build_branches（master / release/*）
    alt 分支不在白名单
        API-->>GL: 200 {ignored: true, reason: branch_not_whitelisted}
    end

    API->>API: 提取 commitId / 作者 / 提交信息
    API->>RD: SET yn:webhook:dedup:{project}:{commit} 1 NX EX 600
    alt 重复推送（去重命中）
        API-->>GL: 200 {ignored: true, reason: duplicate}
    end

    API->>RD: 检查队列长度（超过阈值 → 熔断，避免 Webhook 风暴）
    alt 队列拥塞
        API->>NTF: 告警「构建队列积压」
        API-->>GL: 200 {ignored: true, reason: queue_congested}
    end

    API->>DB: INSERT build_record(trigger_type=webhook, trigger_name=commit 作者)
    API->>DB: INSERT audit_log（Webhook 触发构建）
    API->>Q: push 任务
    API-->>GL: 200 {accepted: true, buildId, buildNo}
```

## 6. 时序图中的关键约束汇总

| 约束 | 实现位置 |
| --- | --- |
| 构建幂等（10 分钟内同 commit 不重复构建） | `POST /builds` + Redis `yn:webhook:dedup` |
| 部署互斥（同环境同服务串行） | Redis `yn:lock:deploy:{env}:{svc}`，TTL 30 分钟 |
| 日志不丢不重（SSE 断线续传） | Redis Stream + `Last-Event-ID` |
| 状态机拒绝非法跃迁 | 服务层统一 `assertTransition(from, to)` |
| 破坏性操作必留审计 | Interceptor 拦 `POST/PUT/PATCH/DELETE` 自动写 `audit_log` |
| 受保护环境二次确认 | `environment.need_approval` + `deploy:approve` 权限点 |
| 镜像清理前校验引用 | `image_record.deployed_envs` + `service_instance.current_image_id` |
| AI 只读 | AI 模块白名单工具集，变更操作返回 action 卡片由用户触发 |
| 上游故障降级 | LLM 超时 → 规则引擎；Harbor 不可达 → 构建失败并明确提示上游不可用（50200） |
